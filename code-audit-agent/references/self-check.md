# Self-Check

**自检流程**: Phase 0 → Phase 1 → Phase 2A → Phase 2B → Phase 2C → (Phase 2E/2D) → Phase 3 → Phase 3E → Phase 4 → Phase 5

每个审计阶段的自检清单。强制执行，不可跳过。

**[CHECKPOINT: After Each Phase]** 每个阶段完成后，必须执行对应的自检清单，确认所有检查项通过后方可进入下一阶段。

## Phase 0: 初始化自检

首先，确认Phase 0初始化已完成：
- [ ] 执行模式自动检测完成（hybrid/static）
- [ ] agent.md 规则文件已读取（Phase 0 依赖）
- [ ] **新语言检测**: PHP/C#/Rust/Kotlin 指纹文件已识别（如适用）
- [ ] **API安全检测**: OpenAPI/GraphQL 指纹文件已识别（如适用）

## Phase 1: 侦察自检

- [ ] 使用了 Glob 工具（不是凭印象）
- [ ] 技术栈通过指纹文件确认（不是猜测）
- [ ] 对应规则文件已读取
- [ ] 完成了业务上下文收集（环境/接口分类/数据敏感度）
- [ ] 模块敏感度分级完成（CRITICAL/HIGH/MEDIUM/LOW）
- [ ] **API端点**: 已识别 REST/GraphQL/gRPC 端点（如适用）
- [ ] **组件识别**: 后端/前端/客户端/API组件已识别
- [ ] **目录分析**: 各组件源代码目录已确认
- [ ] **依赖关系**: 组件间依赖关系已映射
- [ ] **组件报告**: 项目组件清单已生成

## Phase 2: 分组件审计自检

### Phase 2A: Sink-Driven 审计自检

- [ ] Sink 列表来自 references/sink-libraries.md（不是凭记忆）
- [ ] 每个命中点都做了 ±30 行 Read
- [ ] 数据流追踪回答了 Q1/Q2/Q3
- [ ] 执行了跨文件追踪（必要时）
- [ ] 搜索了隐蔽调用链（反射/动态代理/异步）
- [ ] 未将 references/ 中的示例代码当作项目代码
- [ ] MyBatis XML 扫描了 ${} 使用
- [ ] SpEL 使用场景扫描了 #{...} 表达式
- [ ] 字符串拼接场景执行了常量折叠尝试
- [ ] **【强制追溯深度】**: 每个 Sink 点的调用链已向上追溯**至少 5 层**，或已到达 Controller/入口点（以先满足者为准）。仅追溯 2-3 层即停止 → 必须继续追溯
- [ ] 追踪超过7层的条目标记为 UNCONFIRMED
- [ ] **【逐字符比对】**: 每个拟报告的漏洞，已用 Read 工具读取实际代码并**逐字符比对** Sink 调用确实存在于代码中，不是仅凭 Grep 匹配到函数名就下结论
- [ ] **【Grep ≠ 验证】**: Grep 仅用于定位候选代码，**真正的验证必须通过 Read 读取实际代码**。不存在"Grep 到函数名就报告"的情况
- [ ] **新语言支持**: PHP/C#/Rust/Kotlin Sink 检测已执行（如适用）
- [ ] **API安全**: REST/GraphQL/gRPC 专项 Sink 检测已执行（如适用）
- [ ] **范围限定**: 仅扫描目标组件目录，未跨组件扫描

### Phase 2B: Control-Driven 审计自检

- [ ] 搜索了全部通用检查项（硬编码密钥/调试模式/CORS/认证缺失/TLS配置）
- [ ] 执行了语言专项检查项
- [ ] 排除了环境变量引用的假阳性
- [ ] 执行了补偿逻辑检测（防止误报）
- [ ] **【全项目范围补偿搜索】**: 补偿逻辑检测（Filter/Interceptor/Middleware/网关防护）已在**全项目范围内**搜索，不仅限于当前模块。搜索范围包括：所有 `*Filter.java`、`*Interceptor.java`、`*Middleware.*`、`WebSecurityConfig.*`、网关配置文件
- [ ] **【净化匹配精确度】**: 对每个净化函数命中点，已用 Read 工具读取命中代码的 **±30 行上下文**，确认净化函数确实在数据传递路径上被调用，不是注释中的代码、不是不同上下文中的同名方法、不是条件分支中永远不满足的路径
- [ ] **组件隔离**: 各组件独立检测，未混用规则

### Phase 2C: Logic-Driven 审计自检

- [ ] 执行了权限控制逻辑检查（IDOR / 垂直越权）
- [ ] 金融场景已触发金额/竞态条件检查
- [ ] 识别了状态字段并检查了状态机逻辑
- [ ] 检查了关键操作的幂等性

## Phase 2J: 联合审计自检

- [ ] **数据流追踪**: 已识别跨组件数据流
- [ ] **前端→后端**: 前端发现的后端影响已评估
- [ ] **后端→前端**: 后端发现的前端放大已评估
- [ ] **客户端影响**: 移动端发现的影响范围已评估
- [ ] **共享代码**: 共享库问题是否影响所有组件已检查
- [ ] **攻击链验证**: 完整攻击链可行性已验证
- [ ] **风险调整**: 跨组件风险等级调整已记录

## Phase 2E: 前端安全审计自检

- [ ] 识别了前端技术栈类型（Vue/React/Angular/小程序/jQuery）
- [ ] 搜索了所有危险 Sink（innerHTML / eval / document.write 等）
- [ ] 对每个危险 Sink 追踪了数据来源（污染链分析）
- [ ] 检查了本地存储是否明文存储敏感信息
- [ ] 检查了前端是否有鉴权绕过风险
- [ ] 检查了敏感信息硬编码（API密钥、AppSecret等）
- [ ] 检查了 CORS 配置（AllowAll + credentials 同时出现）
- [ ] 检查了 URL 跳转是否有白名单限制
- [ ] 对小程序项目检查了 appid/appsecret 是否硬编码
- [ ] 所有前端发现均基于源码文本

## Phase 2D: 动态验证自检（仅 hybrid 模式）

- [ ] 备份文件 HTTP 访问验证完成
- [ ] CORS OPTIONS 预检请求已发送
- [ ] 条件编译验证（如有编译环境）
- [ ] 反射调用链激活路径分析
- [ ] 未授权访问验证
- [ ] **可利用性验证**: sqlmap/XSS PoC 命令已生成
- [ ] **Kill Chain分析**: 攻击链分析已生成（如启用）
- [ ] **【新增】未授权接口验证**: 对疑似未授权的接口，已尝试匿名访问确认是否真的无需认证
- [ ] **【新增】JWT 过期验证**: 对疑似无过期时间的 JWT，已解码确认 payload 中无 `exp` claim
- [ ] **【新增】注销 Token 失效验证**: 登录→注销→使用原 Token 重放，确认是否仍可用
- [ ] **【新增】Actuator/Swagger/Nacos 暴露验证**: 已尝试访问 `/actuator/env`、`/v3/api-docs`、`/nacos/index.html`
- [ ] **【新增】SSRF 内网探测验证**: 对疑似 SSRF 点，已尝试访问 `127.0.0.1:8080` 或云元数据地址
- [ ] **【新增】验证码一次性验证**: 获取验证码→使用一次→再次提交同一验证码，确认是否仍可验证通过
- [ ] **【新增】负数金额绕过验证**: 对前端有限制但后端未校验的数值参数，已尝试传入负数/小数确认后端是否拦截
- [ ] **【新增】邮箱轰炸验证**: 已尝试在邮箱前后加空格提交，确认是否可绕过格式校验和频率限制

## Phase 3: 静态验证自检

- [ ] 每个漏洞都经过文件存在性验证
- [ ] 每个漏洞都经过代码真实性验证（逐字符比对 Read）
- [ ] 每个漏洞都经过可达性验证
- [ ] 执行了纯静态补偿逻辑验证（第四重）
- [ ] 执行了污染链回溯验证（第五重）
- [ ] 置信度已正确标注（含 GREY/UNCONFIRMED 分类）
- [ ] 每个灰色条目均经过准入确认
- [ ] 每个灰色条目均计算了纯静态风险得分
- [ ] 按分值完成了分流（≥15升漏洞 / 5-14中风险 / <5低风险）
- [ ] 中高风险灰色（≥5分）均执行了纯静态深度分析
- [ ] **误报过滤**: 已执行 false-positive-filter 规则验证
- [ ] **可利用性评估**: 已计算漏洞可利用性评分
- [ ] **CVSS评分**: 每个漏洞已计算CVSS v3.1评分和向量
- [ ] **攻击路径**: 启用 `--attack-path` 时攻击路径图已生成

## Phase 3E: 跨项目确认自检

- [ ] 每个候选漏洞都已找到明确的外部入口点（Controller/MQ/RPC/WS）
- [ ] 从入口到 Sink 的每一步调用关系都已 Grep 验证
- [ ] 数据流链路完整：用户输入 → ... → Sink 参数，中间无断裂
- [ ] Sink 的危险参数来源已确认：用户输入而非配置/常量/系统生成
- [ ] **【全项目范围补偿搜索】**: 已在全项目范围内搜索全局过滤器/中间件/网关防护（不限于当前模块）。搜索范围：所有 `*Filter*`、`*Interceptor*`、`*Middleware*`、`WebSecurityConfig*`、`SecurityFilterChain*`、网关配置文件、Nginx 配置
- [ ] **【净化函数 ±30 行确认】**: 对每个净化函数命中点，已用 Read 工具读取命中代码的 **±30 行上下文**，确认净化函数确实在数据传递路径上被调用，不是注释中的代码、不是不同上下文中的同名方法
- [ ] **【逐字符比对 Read 输出】**: 对每个拟报告的漏洞，已将 Read 工具返回的实际代码与候选漏洞进行**逐字符比对**，确认危险代码（如 `stmt.execute("SELECT..." + userInput)`）逐字符存在于代码中。如果 Read 输出与预期不符 → 不报告
- [ ] 已在项目范围内搜索输入校验注解（@Valid/@Validated）
- [ ] 已在项目范围内搜索输出转义/XSS 防护
- [ ] 多模块项目已追踪到最外层入口，非仅看业务模块
- [ ] 共享库漏洞已验证至少一个引用方有完整攻击链
- [ ] 条件编译/环境依赖的危险代码已确认生产环境可触发
- [ ] 6项确认清单中 ≤4 项通过的条目已从报告中剔除
- [ ] 不存在仅基于单文件/单函数就报告的漏洞
- [ ] **【强制 Read 验证】**: 每个报告的漏洞都已用 Read 工具读取 Sink 点代码（±30行）、入口点代码（±30行）、至少一个中间节点代码（±30行）
- [ ] **【禁止仅凭 Grep 报告】**: 不存在仅凭 Grep 匹配到函数名就报告的漏洞
- [ ] **【三段读取验证】**: Sink 点 + 入口点 + 中间节点 的实际代码均已确认，不是注释或死代码

- [ ] **端报告内容**: 每个端报告仅包含该端的漏洞，按 CRITICAL → HIGH → MEDIUM → LOW → INFO 排序

- [ ] **【仅报告安全漏洞】**: 已逐项审查所有拟报告条目，确认均为安全漏洞（可被攻击者利用破坏机密性/完整性/可用性）。**不存在**以下非安全类条目：N+1 查询性能、空指针/缺少 null 检查、低效算法、未使用的 import、代码风格问题、架构设计决策、内存泄漏（不可利用的）、竞态条件（与安全无关的）、代码重复、硬编码魔法数字
