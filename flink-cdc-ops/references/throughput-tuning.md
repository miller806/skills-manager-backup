# 快照阶段吞吐量化

配套脚本：`scripts/split_durations.py`（只读日志，不改状态）。

## 一、先分清「慢」和「卡」

快照阶段单表跑几分钟是常态。判定卡死的唯一硬标准是 **split 起止差集里那条的时间不再增长**，不是算子计数不动（换表间隙计数本来就不动）。

## 二、按表大小分组算吞吐

把 split 按导出记录数分组，算每组的「合计条数 ÷ 合计秒数」。典型形态：

```
≥8000 条      平均 63 秒/个    128 行/s
2000-8000     平均 18 秒/个    120 行/s
100-2000      平均  7 秒/个    101 行/s
<100 条       平均 0.2 秒/个   154 行/s
```

各组吞吐在同一个量级 → **瓶颈是共享的链路带宽/RTT，不是单表处理逻辑**。推论：

- 加 `scan.snapshot.fetch.size`、减往返次数，只省「往返次数 × RTT」这一项。先把这项算出来：8052 行 ÷ 1024 × 120ms ≈ 1 秒；若实测该表要 136 秒，差两个数量级 → 慢在数据体量本身（大字段 + 带宽），调 fetch size 无意义。
- 只有加 `parallelism`（多 split 并发读）能真正缩短，但受下一条限制。

若某组吞吐明显掉队（比如大表只有小表的 1/3），才是单表层面的问题：宽行、BLOB、无主键/无索引导致全表扫。

## 三、parallelism 天花板

`p` 条并行通道的最短总时长 ≈ max(最长单 split 的耗时, Σsplit 耗时 ÷ p)。这是一个装箱问题，用最大堆贪心仿真即可（脚本已实现）。

示例（95 个 split、合计 756 秒、最长单 split 136 秒）：

```
p=1   756s  1.00x
p=2   378s  2.00x
p=4   189s  4.00x
p=6   136s  5.56x   ← 已等于最长单 split
p=8   136s  5.56x   ← 再加无收益
```

**报告给用户时要打折扣**：若吞吐受共享带宽限制，并发读会均分同一条链路，实际加速通常只有理论上限的一半左右（`p=4` 理论 4x，实测能到 2-2.5x）就已经不错。

**硬约束**：`p` ≤ 该 pipeline 的 `server-id` 段宽度。`server-id: 5500-5504` 只能跑 5 个 subtask，`p=6` 会让两个 subtask 撞同一段 server-id，复现 server-id 冲突。

## 四、逐 split 的固定开销

快照阶段每个 split 结束后会建一次 binlog 连接补这段快照期间的增量：

```
Finished exporting 8095 records for split 'x'
Connected to MySQL binlog at <host>:3306      ← 建立
Stopped reading binlog after 0 events         ← 断开
Exporting data from split 'y'
```

跨境链路下单次 2-3 秒。统计口径：`grep -c 'Connected to MySQL binlog'`（注意先按源库 IP 收窄，否则混入别的作业）。

大量空表/小表时这项占比可观（N 张表 × 2-3 秒）。收窄 `tables` 白名单能直接砍掉，但会改变同步范围 —— 空表现在空不代表以后空，必须让用户决定。

## 五、汇报格式

用户要的是「改什么、能快多少、风险是什么」，不是过程。给三段：

1. 现状数字（split 数、总条数、总耗时、当前平均吞吐）
2. 仿真表（p → 秒 → 加速比 → 是否触到天花板）
3. 天花板成因 + 打折后的实际预期 + 硬约束（server-id 段宽度）

同时明确优先级：全量快照只跑一次，binlog 增量跑 7×24。若历史故障都在 binlog 阶段，优化快照只是「开局少等十几分钟」，不能替代 binlog 稳定性验证。
