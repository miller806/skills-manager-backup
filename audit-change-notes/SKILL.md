# 安全审计变更记录

回答：本次哪些功能变化、现在如何工作、从哪里定位代码。正文以功能为主，仅补充与变化相关的审计线索。

## 确定范围

- 先读仓库规则、既有版本文档及工作区状态；沿用目标项目的文档目录、命名与归属。用户指定飞书、Obsidian 或本地位置时遵从指定；未指定时可先在对话交付，不擅自创建发布文档目录。
- 使用用户指定的基线和目标 tag、commit 或 PR，解析到实际 SHA。多仓库分别记录范围；工作区改动单独标记。不要默认用开发分支替代尚未创建的发布 tag，不把未发布内容称为已发布。
- 发布内容比较两个端点，如 `git diff <base> <target>`。仅在明确比较 PR 分支相对分叉点的改动时使用三点 diff，并说明口径。提交日志只用于发现线索，以实际差异为准。
- 范围不明确时先检查发布记录和可用引用，再询问影响正确性的缺失信息；可以整理草稿，但注明范围待确认。
- 仅有需求或外部文档时注明“依据材料整理，未核对代码”，不得虚构 SHA、文件或验证结论。外部文档通过可用连接器或对应文档技能读取；无法访问则说明限制。

- 开始时确认前端与后端代码位置和各自版本范围；不同仓库的 tag/SHA 分别解析，不能假定同名版本或相同发布时间。前端代码不在当前仓库且位置未知时，主动请用户提供前端代码的本地路径（有多个前端项目时分别提供），并询问无法确定的比较范围；等待期间可以继续后端整理。用户明确只整理某一端时遵从其范围。
- 缺少前端代码时，前端标记“待补充：未提供前端代码位置，尚未核对”；不能写成“无前端改动”，也不能凭后端接口、静态包名称或需求描述推断实际前端实现。已核对指定范围没有变化才写“本次无前端改动”。后端材料缺失时同理。

## 归纳功能

1. 查看 diff 的 stat、name-status、提交记录及实际差异，再按需读上下文，覆盖新增、删除、重命名文件以及 SQL、配置、路由、任务、消息和依赖变化。
2. 前端、后端分别按业务目的归并跨服务、跨提交改动，如退款、代付归集、订单导出。不要逐提交翻译，不按 Controller、Service、SQL 拆分同一功能。
3. 标记新增、调整、修复、移除；说明业务对象、触发条件和结果。调整/修复写清原行为和新行为。无行为变化的格式或重构通常不进入正文；未理解的改动先核对，不能直接省略。
4. 接口核对类与方法映射、HTTP 方法、网关前缀/重写及调用方；涉及认证权限时再追踪过滤器、拦截器和业务校验。区分对外路径和服务内路径，无法确认则标为待确认。
5. 数据、配置、异步和依赖只补充与功能、兼容性或审计定位有关的对象，不堆砌全部内部实现。

前端条目关注页面/路由、用户操作流程、表单校验、展示与交互、接口调用及登录/权限交互的实际变化；提供页面、组件或请求模块的代码依据。前端按钮显隐与校验不等于后端授权。跨端同一功能分别说明各端变化，并使用相同功能名称互相引用，避免重复描述整套业务。

## 写作要求

默认读取并使用 [references/format.md](references/format.md)；用户有模板时保留其有用结构。

- 默认采用“功能总览表 + 功能详情”：总览按“前端改动”“后端改动”分表，分别列编号、功能、类型、涉及项目/服务、变更摘要；详情沿用同一编号，以短列表解释业务变化和审计定位，不重复抄写总览摘要。详情也按“前端改动”“后端改动”分节，编号分别用 F1、B1，跨端功能互相引用。仅有一两项简单变化时可省略总览表，但保留前后端分区及覆盖状态。
- 根据内容选择局部表格：同一功能有多个接口时用“变化、方法、完整路径、用途”；有多个行为调整点时用“变更项、原行为、新行为”。单个入口或一句话能讲清的变化保留短列表，不强制套表。
- 保持表格单元格简短，不将长段说明、代码清单或多条路径塞进同一格，不使用嵌套表格。解释和代码依据放在表格外；较长技术清单按需移到附表。Markdown 表格注意转义单元格内的竖线。
- 每项包含功能名称与类型、涉及项目/服务、功能变化和代码依据。有接口则列入口，其余字段按需出现，不填一串“无”。
- 接口写完整 `HTTP 方法 + 路径` 并区分新增/修改/移除，不用 `/info`、`/apply` 等相对缩写。大量同类查询可移入附表，正文保留关键写入口及代表性查询，注明完整清单位置。
- 相关时补充公网/免登录入口、签名、权限、租户或归属边界、资金操作、数据导出、第三方回调的实际变化。通常放在对应功能下，仅跨功能变化集中说明。
- 注解不等于运行时结论：`@SaIgnore` 不代表没有其他认证，`@Sign` 不证明验签有效，“内部 RPC”不证明网络隔离，权限标识存在不证明执行了校验。陈述已追踪到的机制与边界，不把静态结论写成线上验证。
- 不写“安全无风险”“通过审计”，不强制逐项评级。发现可信安全问题时单独提示，不将记录扩展为漏洞报告。
- 代码依据提供仓库相对路径及类/方法；可补充目标 SHA 的永久链接或准确行号，不猜测远程地址和行号。跨服务条目覆盖关键入口及核心行为即可。
- 配置只列键、作用和已确认的默认值，不复制密钥、令牌或真实个人数据。数据迁移是否执行、路由是否生产生效，必须另有证据。

## 检查与交付

- 将条目反向核对文件差异，关注删除入口、新服务、SQL/配置、网关、任务/消息和依赖是否遗漏；合并重复描述。
- 核对行为、接口和证据一致，不将旧接口写为新增、计划写为实现、编译通过写为部署成功。
- 总览与详情的功能编号、类型及范围一致；局部表格只在便于比较或检索时使用，不因排版压缩掉关键行为和证据。
- 待确认项只列影响范围或理解的具体缺口；材料不足不声称完整覆盖。说明实际核对范围和验证方式；仅生成文档通常无需运行应用测试，引用测试结果必须有执行依据或注明来源。
- 默认交付中文 Markdown。发布/覆盖外部文档或发送给安全团队，仅在用户已授权的目标和范围内执行；生成记录本身不包含这些动作。用户只要求技能时不修改参考云文档。
